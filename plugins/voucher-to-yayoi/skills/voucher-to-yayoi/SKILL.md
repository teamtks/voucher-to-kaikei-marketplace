# 証憑書類 → 弥生会計インポートデータ 作成スキル

## このスキルの考え方

証憑書類(領収書・請求書)から仕訳を起票する作業では、日付・金額・取引先の読み取りに
高い精度が必要になる。ローカルのOCR(文字認識)だけでは、桁の誤読や複雑なレイアウトへの
対応に限界があることが実際の運用で確認されている。そのため、このスキルでは**証憑の
内容理解そのものはClaude自身の画像読解に任せ**、機械的に決まる部分(弥生形式への
変換ルール)だけをスクリプトに固定化している。

ただし、証憑画像には自社名(宛名)や取引先の機密情報が含まれるため、**画像をそのまま
Claudeに渡すのではなく、宛名部分だけをローカルで黒塗りしてから読み取る**という手順を
必ず踏むこと。これは情報漏洩対策として利用者と合意した重要なルールであり、省略しては
ならない。

## このスキル自身の実際の場所を特定する(毎回、他の何よりも先に確認すること)

以降の手順で`scripts\...`と書かれているコマンドは、**作業ディレクトリ(案件フォルダ)
の中には存在しない**。案件フォルダはランチャー経由で開いた作業対象のフォルダに
過ぎず、スキル自身の実体はそことは別の場所にある。`scripts\...`という相対パスを
そのまま作業ディレクトリで実行しようとすると「ファイルが見つかりません」になるので、
**先に実際の絶対パスを特定してから、以降はその絶対パスを使ってコマンドを組み立てる
こと**。インストール方法によって場所が変わる:

- **マーケットプレイス経由でインストールされている場合**:
  `<ユーザーのホームフォルダ>\.claude\plugins\cache\voucher-to-yayoi-marketplace\voucher-to-yayoi\<バージョン番号>\skills\voucher-to-yayoi\`
  (バージョン番号のフォルダ名は環境ごとに異なるため、`refresh_marketplace_cache.py`を
  探すなどして実際の値を特定すること。例:
  `Get-ChildItem -Recurse -Filter refresh_marketplace_cache.py "$HOME\.claude\plugins\cache"`)
- **このスキルフォルダを直接使っている場合**: `<ユーザーのホームフォルダ>\.claude\skills\voucher-to-yayoi\`

特定できたら、以降このドキュメント内で`scripts\...`と書かれている箇所はすべて
`<このSKILLフォルダ>\scripts\...`に読み替えて実行する(このセッション中は同じ場所の
はずなので、毎手順で探し直す必要はない)。

## スキルの内容を常に最新化する(毎回、他の作業より先に自動実行すること)

Claude Desktopの「プラグイン」画面にある「同期」ボタンは、内部的に持っている
マーケットプレイスの複製を実際には更新しないことがある(実機で確認済みの不具合)。
そのままだと、GitHub上で新機能や修正を配布しても、利用者の手元では反映されない。

これを利用者に気づかせたり、設定画面を操作させたりする必要は無い。**このスキルを
使う作業を始めるたびに、他の何よりも先に、必ず以下を1回実行すること**(`python`が
まだ使えない場合は、後述の「Pythonが入っていない場合」を先に行ってから実行する):

```
python <このSKILLフォルダ>\scripts\refresh_marketplace_cache.py
```

**このスクリプトだけは、venvではなくシステムのPython(上記のとおり`python`)で
実行すること。** マーケットプレイス経由でインストールした場合、venvは更新対象の
フォルダの中にあるため、venvのPythonで実行すると使用中のファイルを消せず更新
できない(この取り違えにより、他のPCのスキルが古いまま何度も更新されない事象が
実際に起きた)。なお現在は、venvのPythonで実行された場合でも自動的にシステムの
Pythonへ切り替えて実行し直すようになっている。

これは、マーケットプレイス経由でインストールされている場合にのみ動作し、内部の
複製を安全な方法(早送りマージのみ、強制上書きはしない)で最新化した上で、実際に
読み込まれるキャッシュフォルダの中身を最新の内容に置き換える。Claude Desktop
アプリ自身が管理する設定ファイルには一切触れない(そのため、プラグイン画面上の
「最終更新日」表示は更新されないままになるが、これは見た目だけの問題であり、
実際にスキルが使う内容は正しく最新化される。利用者から見た目の日付について
聞かれた場合は、その旨を説明すること)。マーケットプレイス経由でない場合
(このスキルフォルダを直接使っている場合)や、オフラインの場合は、何も行わずに
そのまま次に進んでよい。

なお、この最新化によってキャッシュフォルダの中身(このSKILL.md自体を含む)が
置き換わることがあるが、**今読んでいるこのセッションの内容が自動的に入れ替わる
わけではない**(次に新しいセッションを開始した時から反映される)。

**それでも古い内容のままの場合(利用者から「新しい機能が動いていない」と言われた
場合)は、状態を調べる専用スクリプトを使うこと。** 内部クローンが途中で壊れて
早送りマージできなくなっているなど、上の最新化が安全側に倒れて何もせず終わって
いることがある(実際に複数のPCで発生した)。

```
python <このSKILLフォルダ>\scripts\doctor.py
```

これは調べるだけでファイルを一切変更しない。インストール形態・GitHubとの差・
このPC内にあるSKILL.mdがそれぞれ最新かどうかを一覧で表示し、最後に「何をすれば
よいか」を判定して出す。判定に従い、修復が必要と出た場合は次を実行する:

```
python <このSKILLフォルダ>\scripts\doctor.py --repair
```

こちらは内部クローンをGitHub上の内容に強制的に合わせ(早送りできない状態でも
確実に揃う)、実際に読み込まれるキャッシュへ反映する。Python実行環境(venv)は
保持されるため作り直しは不要。Claude Desktopアプリ自身が管理する設定ファイルには
一切触れない。実行後は**新しいセッションを開始**することで反映される。

## 初回セットアップ(利用者に手作業をさせず、Claude自身が毎回自動でチェック・実行すること)

このスキルを使う作業を始める前に、まず`scripts/.venv`フォルダが存在するかどうかを
確認する。**利用者に「セットアップしてください」と案内するのではなく、Claude自身が
以下を実行して、利用者には完了報告のみを行う。** 存在しない場合(初めてこのPCで
このスキルを使う場合)は、以下を実行してから作業を進める:

```
cd <このSKILLフォルダ>/scripts
python -m venv .venv
.venv\Scripts\pip install -r ../requirements.txt
```

(このセットアップ時のみインターネット接続が必要。以降は完全にローカルで動作する。
セットアップ完了後は、`scripts/.venv/Scripts/python.exe` で各スクリプトを実行する。)

このvenvは、上の最新化(`refresh_marketplace_cache.py`)でスキルの内容が入れ替わっても
引き継がれるため、更新のたびに作り直す必要は無い。ただし、最新化の結果に
「必要なライブラリの一覧(requirements.txt)が変わっています」と表示された場合だけは、
既存のvenvの中身が古いので、`.venv\Scripts\pip install -r ../requirements.txt` を
実行し直すこと。

Pythonそのものがこのパソコンに入っていない場合は、`python`コマンドがエラーになる。
その場合は、利用者に「Pythonをインストールしてほしい」と伝えるのではなく、Claude自身が
`winget install --id Python.Python.3.12 -e --accept-source-agreements --accept-package-agreements --silent`
のようなコマンドでインストールしてから、上記のセットアップに進むこと(これも本日の
プロジェクトで実際に行った手順であり、非技術者の利用者に手作業をさせるべきではない)。

venvのセットアップに続けて、デスクトップに案件選択用のランチャー(ショートカット)が
まだ無い場合は、以下も実行する(これも利用者に手作業をさせず、Claude自身が行うこと)。

```
scripts\.venv\Scripts\python.exe scripts\setup_launcher.py
```

これにより、デスクトップに「仕訳.TeamTKS.lnk」というショートカットが作成される。
利用者はこれをダブルクリックすることで、案件フォルダの一覧表示・新規作成・
Claude Desktopでの起動(該当フォルダを作業ディレクトリにしたCodeセッションを開く)
ができるようになる。初回起動時は案件フォルダをまとめて置く場所(ルートフォルダ)を
選ぶダイアログが表示され、以降はその場所が記憶される(このランチャーの設定は
`%APPDATA%\voucher-to-yayoi-launcher\config.json`にPCごとに保存される。スキルの
中身自体は他のPCと共通だが、この設定だけはPCごとに独立している)。

## 作業の進め方

### 1. 会計ソフト・課税方式・対象ファイル・参考データを確認する

**まず、作業ディレクトリ(案件フォルダ)に`CLAUDE.md`があるか確認する。** 通常は
ランチャーの「＋新規プロジェクト」で作成した時に自動で付くが、**既存のフォルダを
手作業で用意し、ランチャーの「置き場所を変更」でその親フォルダを指定して取り込んだ
場合は、`CLAUDE.md`が作られない**(この不具合で会計ソフト・課税方式の確認自体が
行われなかったことを確認済み)。無ければ、このスキル自身の場所(前述の手順で特定
済みのはず)のランチャー本体を使って補う:

```
python -c "import sys; from pathlib import Path; sys.path.insert(0, r'<このSKILLフォルダ>\scripts'); import launcher; launcher.ensure_claude_md(Path(r'<案件フォルダの絶対パス>'))"
```

既に`CLAUDE.md`がある場合は何もしない(中身を上書きしない)。これで作成された場合は、
以降の手順で説明する各項目(会計ソフト・課税方式など)が「未確認」から始まる。

**証憑を読み始める前に、まず次の2点を確認する。** どちらも作業の途中で判明すると
作り直しになるため、最初に片付ける。**いずれも案件フォルダの`CLAUDE.md`に記録が
あればそれを使い、聞き直さない。** 利用者から聞き取って判明した場合は、次回以降の
ために`CLAUDE.md`へ記録すること(記録の書式は後述の「案件固有の気づきを
CLAUDE.mdに記録する」を参照)。

**(1) 出力先の会計ソフト(弥生会計 or 会計大将)** — 作れる仕訳の形が変わる:

- **弥生会計**: 複合仕訳・補助科目とも使える(制限なし)。
- **会計大将**: 1伝票1明細の単純仕訳のみで、補助科目は使えない。さらに勘定科目の
  数値コード表(JSON)が別途必要になる(手順6b参照)。複合仕訳が必要な証憑が
  含まれている場合は、その時点で利用者に相談すること。

**(2) 消費税の課税方式(本則課税 or 簡易課税)** — 売上の税区分名が変わる。
**簡易課税の場合は、事業区分が第何種かも必ず併せて確認する**(第一種〜第六種)。
簡易課税では売上の税区分名に事業区分が入るため(例: 第六種事業なら
`課税売上込六10%`)、種別が分からないと正しい税区分を作れない。手順4のJSONに
`"sales_business_type": "六"`として入れると、チェック資料の税区分の選択肢が
その事業区分の名称で作られる(本則課税の場合はこの項目を入れない)。
なお仕入側の税区分は課税方式によらず同じ(`課対仕入込10%適格`など)。

続いて、ユーザーに次の2点を確認する(会話の中で既に分かっていれば聞き直さなくてよい):
- 処理する証憑ファイル(PDF/JPG/PNG)のパス(ランチャー経由の場合は案件フォルダの
  「証憑書類」フォルダの中身)
- その案件(顧問先)の勘定科目一覧・キーワード対応表のExcelファイルのパス(ランチャー
  経由の場合は案件フォルダの「参考資料ファイル」フォルダの中身)
  (無ければ、ひとまず参考データ無しで進めてよいか確認する)

**「参考資料ファイル」フォルダの中身(勘定科目一覧・キーワード対応表・過去の元帳など)
は、あくまで科目やルールを判定するための参照データであり、それ自体を仕訳の対象に
してはならない。** 仕訳を起票する対象は必ず「証憑書類」フォルダに入っている証憑
ファイルのみである。この2つを取り違えると、参考資料の中身から誤って仕訳を生成して
しまう事故になるため、対象ファイルと参考データのどちらがどちらか、作業前に必ず
明確に区別すること。

参考データがある場合は、内容を把握するために以下を実行して結果を読む:

```
scripts\.venv\Scripts\python.exe scripts\print_reference.py "<勘定科目一覧.xlsx>" "<キーワード対応表.xlsx>"
```

### 2. 自社を特定できる情報を黒塗りする(必ず実行すること・省略禁止)

証憑ファイル1件ごとに以下を実行する。PDFは自動でページごとの画像に変換される。

```
scripts\.venv\Scripts\python.exe scripts\mask_addressee.py "<証憑ファイル>" "<作業用フォルダ>"
```

黒塗りするのは**自社(依頼主)を特定できる情報だけ**で、支払先の情報は残す。
文字の見た目だけでは両者を区別できない(レシート・領収証には支払先の住所・電話が
必ず印字されている)ため、書類内での位置と書類の種類も手がかりにして絞り込む:

| 対象 | 黒塗りする条件 |
|---|---|
| 宛名(様/御中で終わる行) | 常に |
| 自社のインボイス登録番号(下記`--own-invoice-no`で指定した番号) | 常に |
| 住所・郵便番号・電話番号 | **宛名の近くにある場合のみ**(＝自社側の記載) |
| 金融機関名・支店名・店番・口座番号・カード会社名・カード番号 | **通帳やカード明細のように、その口座・カードが自社のものである書類の場合**、または宛名の近くの場合のみ |

このため、**宛名の無いレシート(支払先の情報しか印字されていない)では何も黒塗り
されないのが正常**である。「検出されませんでした」と表示されても、それだけでは
異常ではない。

**インボイス登録番号は黒塗りしない**(重要)。領収書・請求書に印字されている登録番号は
通常**取引先(相手方)**のものであり、自社を特定する情報ではない。むしろ手順3で摘要欄に
記載する必要がある情報なので、黒塗りするとその要件を満たせなくなる。例外として、
**自社自身の**登録番号が写り込む書類(自社発行の請求書の控えなど)を扱う場合に限り、
その番号が分かっていれば次のように指定して黒塗りできる:

```
scripts\.venv\Scripts\python.exe scripts\mask_addressee.py "<証憑ファイル>" "<作業用フォルダ>" --own-invoice-no T1234567890123
```

自社の登録番号は、案件フォルダの`CLAUDE.md`の「## この案件で得た気づき」に記録されて
いればそれを使う。作業中に自社の登録番号が判明した場合は、そこに記録しておくと次回
以降も使える(記録の書式は後述の「案件固有の気づきをCLAUDE.mdに記録する」を参照)。

実行結果には「自社を特定できる情報をN件検出し黒塗りしました」または「検出されません
でした」と表示される。**後者は、宛名の無いレシートなど自社の情報がそもそも印字されて
いない証憑では正常な結果である。** ただし、マスク済み画像を手順3で読むときに、自社名や
自社の住所が黒塗りされずに残っていないかは必ず目視で確認すること。残っていた場合は、
検出漏れなのでユーザーに知らせ、対処(その部分を手作業で隠した画像に差し替えるなど)を
相談する。

**この後の手順(3)で読み込んでよいのは、このスクリプトが出力したマスク済み画像
(`<元ファイル名>_masked_pageN.png`)だけである。元のPDF/画像ファイルを直接
読み込んではならない。**

なお、入力がPDFの場合、このスクリプトは黒塗り前のページ画像
(`<元ファイル名>_original_pageN.png`)も同時に出力する。これは手順5のチェック
資料で人間が確認する際に使うためのものであり、**Claude自身がこの画像を読み込む
ことは無い**(ローカルで生成されるHTMLファイルに埋め込まれ、利用者自身のブラウザ
だけで表示されるものであり、外部に送信されることは無いため、黒塗りの必要が無い)。
入力がJPG/PNGの場合は、この複製は作られない(元ファイルそのものが既に存在する
ため)。

### 3. マスク済み画像を読み取り、仕訳を提案する

マスク済み画像をReadツールで開いて内容を確認し、以下を読み取る:
- 取引日付
- 金額(「合計」「ご請求金額」等、最終的に支払う/受け取る金額。小計や内訳の一部と
  混同しないよう、書類全体の文脈から総額を判断すること)
- 取引先名・内容(摘要として使う)
- 勘定科目(手順1で確認した参考データがあればそれを優先して当てはめる。無ければ
  一般的な勘定科目から妥当なものを提案し、その旨をユーザーに伝える。**それでも
  判断できない場合は、仮払金(出金の場合)または仮受金(入金の場合)を使う**)

**自信を持って判断できなかった仕訳には、手順4のJSONで`"needs_review": true`を
付けておくこと**(科目を推測で決めた、金額や日付が読み取りにくかった、仮払金・
仮受金で逃げた、など)。手順5のチェック資料で「🔖 要確認」の付箋として黄色く
表示されるため、利用者がどれを重点的に見ればよいか分かる。**推測した箇所を
黙って確定させないための仕組み**なので、迷ったら付けておく方がよい。
- 税区分(`tax_category`。下表から選ぶ。**弥生・会計大将どちらの出力でも共通の
  一覧**であり、手順6bだけの話ではない)

**税区分(`tax_category`)の一覧**: 借方・貸方の**どちらか一方だけ**に税区分を指定し、
もう一方は`対象外`にする(貸借どちらも実質的に課税取引になることは無い)。

| 値 | 意味 |
|---|---|
| `課対仕入込10%適格` | 課税仕入 標準10%(適格請求書) |
| `課対仕入込10%区分80%`/`区分50%`/`控不` | 同(免税事業者等からの仕入・インボイス経過措置) |
| `課対仕入込軽減8%適格`(区分80%等も同様) | 課税仕入 軽減8% |
| `課対仕入込8%適格` | 課税仕入 8%(旧税率。会計大将出力は未対応) |
| `非課仕入` | 非課税の仕入(支払利息・社会保険料など) |
| `不課税` | 不課税の損益取引(給与・租税公課・海外での支出など) |
| `課税売上込10%`(簡易課税は`課税売上込六10%`のように事業区分の漢数字を挟む) | 課税売上 標準10% |
| `課税売上込軽減8%`(同`課税売上込六軽減8%`等) | 課税売上 軽減8% |
| `課税売上込8%` | 課税売上 8%(旧税率) |
| `非課売上` | 非課税の売上(受取利息など) |
| `対象外` | 消費税区分を持たない取引(貸借科目間の振替など) |

**`不課税`は会計大将側だけの呼び方であり、弥生会計に同名の税区分は無い**
(弥生では両方とも`対象外`を使う)。**弥生でも出力する予定がある仕訳では
`不課税`を使わないこと。** 会計大将側では`不課税`と`対象外`を別物として区別
しており、給与・租税公課のように「損益取引だが消費税の対象にならない」ものは
`不課税`、現金↔預金の移動や預り金の振替のように「そもそも消費税区分を持たない」
ものは`対象外`を使う(会計大将出力でのみ意味を持つ区別)。

簡易課税の事業区分(第○種)は、手順1で確認した種別の漢数字で表す
(第六種なら`課税売上込六10%`)。本則課税で事業区分を使っていない場合は
漢数字なしの`課税売上込10%`を使う。

**免税事業者等からの課税仕入(インボイス制度の経過措置)**は、控除できる額が
消費税相当額の一定割合になる。取引日で判断し、2026年9月30日までは`区分80%`、
2026年10月1日から2029年9月30日までは`区分50%`、それ以降は`控不`とする。

**摘要欄の書き方**: 「取引先名　取引内容(購入品名やサービス内容)」の順で書き、
**証憑にインボイス登録番号(T+13桁)の記載があれば、必ず末尾に付す。**
(例: `FamilyMart横浜スタジアム前店　飲食料品　T8020002045281`)。省略せず、
読み取れた場合は毎回付けること。

取引先名に「株式会社」「有限会社」が含まれる場合は、`㈱`・`㈲`に置き換えて短縮する
(例: `株式会社サンプル商事` → `㈱サンプル商事`)。**これは摘要欄の文字列の中だけの
ルールであり、案件フォルダ名には絶対に使わないこと**(`㈱`・`㈲`をフォルダ名に使うと
Claude Desktopがフォルダを正しく開けなくなる不具合があるため。フォルダ名は
「株式会社」「有限会社」と書くか、ランチャーの自動変換に任せる)。

摘要欄内の**数字とローマ字は必ず半角で書く**(例: `Ｆamily`ではなく`Family`、
`１２３`ではなく`123`)。**カタカナは、文字数に収まらない場合にのみ半角にしてよい**
(基本は全角のままでよく、半角カタカナは字数調整のための手段)。品名・サービス
内容は簡潔にまとめ、点数が多い場合は代表的な1点を挙げて「○○他」のように書く
(例: 複数の食料品→「食料品他」)。

**文字数制限(弥生会計の仕様)**: 摘要欄は全角32文字(半角64文字相当、CP932で
64バイト)までしか入らない。これを超える内容は`generate_yayoi.py`実行時にエラーに
なる。全部を詰め込むと超えてしまう場合は、次の優先順位で削る:
1. インボイス登録番号は最優先で残す(削らない)
2. 取引内容(品名・サービス内容)を「○○他」のようにさらに短くする
3. それでも収まらない場合のみ、取引先名を短縮・省略する

これらは摘要欄の書式であり、証憑画像の黒塗り判定や他のJSON項目には適用しない。

**機種依存文字に注意する**: 取引先名に「﨑」「髙」「德」のような異体字(旧字体・
人名用の特殊な字体)が含まれることがある。これらの一部はCP932の「NEC選定IBM拡張
文字」「IBM拡張文字」という領域の文字で、環境によって文字化けする恐れがある
(実際にこの不具合で仕訳のやり直しが発生したことがある)。`generate_yayoi.py`
実行時に勘定科目・補助科目・摘要・仕訳メモを自動チェックし、該当する文字が
あればエラーで止めて教えてくれる(会計大将出力では摘要・メモをチェックする)。
**自動では置き換えない**(この領域はほぼ人名・地名専用の異体字のため、機械的に
標準字体へ置き換えると実在する方の氏名表記を書き換えてしまう恐れがある)。
エラーが出た場合は、証憑と見比べて正しい字体か確認したうえで、標準的な字体に
直すかそのまま使うかを利用者に確認すること。

**勘定科目名・補助科目名の全角/半角スペースに注意する**: 弥生会計は「横浜銀行 普通」
(半角スペース)と「横浜銀行　普通」(全角スペース)を**別の科目として扱う**。見た目では
区別しにくいため、勘定科目一覧表や総勘定元帳のPDFから科目名を拾う際は、レイアウト上の
見た目(印刷時に均等割り付けされていることがあり、単語の区切りと無関係に文字間へ全角
スペースが挿入されている場合がある)を鵜呑みにせず、実際に登録されている表記を確認する
こと。判断材料がPDFしか無い場合は、pdfplumberで文字単位の座標(`char['x0']`等)を取得し、
不自然に広い間隔がどこにあるか(≒本当の区切り)を機械的に確認するとよい。同様に、
科目名の一部が半角カタカナ(例: `ｷｬﾋﾟﾀﾙ`)で登録されていることもあるため、全角に
安易に変換しないこと。

**補助科目は、既に登録されていることが確認できたものだけを使う。存在するかどうか
自信が持てない場合は、無理に補助科目を作らず空欄にし、区別が必要な情報は摘要欄に
書く。** 過去の元帳PDFに取引先名が書かれていても、それが実際に「補助科目」として
登録されているとは限らない(単に摘要欄の説明文の一部としてレイアウト上たまたま
科目名の隣に印字されているだけの場合がある)。誤って未登録の補助科目名を
`generate_yayoi.py`の出力に含めると、弥生会計へのインポート時に「補助科目
マッチングリスト」画面が表示され、すべて「作成」(＝新規作成)と判定されて
利用者の意図しない補助科目が大量に作られてしまう。**取引ごとに未登録の補助科目を
勝手に作成することは絶対に避けること。** インポート時にこの画面が表示された場合は、
「作成」と判定された行の補助科目名をすべて空欄に戻して再生成し、利用者に確認する。

なお、補助科目名にも文字数制限があり(実測ではおよそ全角20文字＝CP932で40バイト
前後)、これを超えると弥生会計側で末尾を切り詰めた結果として「先頭または末尾に
空白を含めることはできません」という一見わかりにくいエラーになることがある。
補助科目名は摘要欄以上に短く保ち、詳細は摘要欄に書くこと。

複数の証憑をまとめて処理する場合も、1件ごとに上記を読み取ったうえで、**全件まとめて
表形式でユーザーに提示し、確認・訂正を受け付けてから次に進む。** 金額や勘定科目を
自動で確定させて先に進めてはならない — この一手間が、読み取り誤りをそのまま弥生に
取り込んでしまう事故を防ぐ最後の砦になる。

なお、証憑ごとの支払方法(現金・預金口座など、仕訳の貸方または借方の相手科目)が
文脈から不明な場合は、ユーザーに確認する。

### 4. 確定した仕訳をJSONにまとめる

ユーザーが内容を確認・訂正したら、以下の形式のJSONファイルを作成する(1証憑=1つの
voucher_id)。

**単純仕訳(借方・貸方とも1科目ずつ)の場合**は、そのままの内容を1つのlegとして書く:

```json
{
  "start_denpyo_no": 1,
  "legs": [
    {
      "voucher_id": "20260702_familymart",
      "leg_no": 1,
      "transaction_date": "2026-07-02",
      "closing_flag": "",
      "debit":  {"account": "会議費", "sub_account": "", "department": "", "tax_category": "課対仕入込10%適格", "amount": 745, "tax_amount": 0},
      "credit": {"account": "現金", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 745, "tax_amount": 0},
      "description": "FamilyMart横浜スタジアム前店　飲食料品",
      "memo": "",
      "split_side": null,
      "needs_review": false,
      "source_image": "<その仕訳の元になった、黒塗り前の画像ファイルパス>"
    }
  ]
}
```

**複合仕訳(1つの証憑で3行以上になる、または借方・貸方どちらかを複数科目に分ける
場合)は、必ず`split_side: "manual"`を使い、最終的に弥生に出力される行と1対1で
対応する形でlegを作ること。** 自動判定(片方の科目が全明細で同じであることを
Claudeが検出して自動的に「複合」に置き換える方式)は使わない。理由: 自動判定用の
JSON(各legの両側に実科目を入れる形)は、手順5のチェック資料でそのまま表示すると
「同じ科目が複数回登場している」ように見えてしまい、実際に生成される仕訳(合計行＋
複合プレースホルダー)と見た目が一致せず、ユーザーが確認しづらい。`manual`形式なら
チェック資料の表示がそのまま最終結果になるため、確認しやすい。

`manual`形式の作り方: まず、借方・貸方のどちらか一方に「全明細で共通の実科目
(現金や預金口座など)」があるかどうかを見る。あれば、その側を「非分割側」とする。
(例: 税理士報酬44,000円のうち39,916円を現金で支払い、4,084円を源泉徴収して
預り金に計上する場合、借方の「報酬手当」が非分割側)

1. **先頭行(合計行)**: 非分割側に実科目・合計金額を入れ、分割側は
   `{"account": "複合", "sub_account": "", "department": "", "tax_category": "対象外", "amount": <合計>, "tax_amount": 0}`
   にする。
2. **以降の行(明細1件につき1行)**: 分割側に実科目・その行individual金額を入れ、
   非分割側を`{"account": "複合", ...}` (金額はその行と同じ)にする。
3. 全legに`"split_side": "manual"`を指定する。

借方・貸方のどちらにも「全明細で共通の実科目」が無い場合(両側とも明細ごとに
異なる)は、証憑書類からの自動起票では通常発生しないパターンなので、ユーザーに
どう処理すべきか確認すること。

`start_denpyo_no`は、既存の帳簿から続けて採番したい場合はユーザーに確認する(省略時は1)。
`transaction_date`はISO形式(YYYY-MM-DD)で書く。`closing_flag`は通常空文字列で、決算整理
仕訳の場合のみ`"本決"`とする。

`source_image`には、次の手順のチェック資料(人間が確認するためのHTML)に表示する
画像のパスを入れる。**ここは手順3でClaudeが読み取ったマスク済み画像ではなく、
黒塗り前の画像を指定すること**(JPG/PNG入力の場合は元の入力ファイルそのもの、
PDF入力の場合は手順2で追加出力された`<元ファイル名>_original_pageN.png`)。
チェック資料はユーザー自身のローカル環境だけで開くファイルであり、Claudeがこの
画像を読み込むことは無いため、黒塗りされていない元の内容を見せた方が、ユーザーが
証憑の全体を見比べて確認しやすくなる。同じvoucher_idの明細は同じ証憑から来ている
はずなので、同じ`source_image`を指定する。

### 5. チェック資料(HTML)を作成し、その場で確認・訂正してもらう

弥生形式のファイルをいきなり作る前に、**証憑画像と仕訳内容を並べて見比べられる
チェック資料を必ず作成し、ユーザーに最終確認してもらう。** これは「読み取り内容を
鵜呑みにせず、証憑と見比べて確認する」という本スキルの基本方針を、実際に見比べやすい
形にしたものであり、省略してはならない。

```
scripts\.venv\Scripts\python.exe scripts\generate_review_html.py "<手順4のJSON>" "<出力先>\仕訳チェック資料.html"
```

出力されたHTMLファイルは、ブラウザで開くと右側に仕訳の一覧、左側にクリックした仕訳の
元になった証憑画像が表示される。**このHTML画面上で、勘定科目・金額・摘要・日付などを
直接入力し直して訂正できる。** チャットに戻って伝え直す必要はない。

証憑の文字が小さくて読みにくい場合は、**画像を拡大できる**。画像の右上に出る
「−／＋／全体」ボタン、マウスホイール、ダブルクリックのいずれでも操作でき、
拡大中はドラッグで見たい位置に動かせる(「全体」で元の表示に戻る)。利用者から
「小さくて読めない」と相談された場合はこの操作を案内すること。

**税区分はドロップダウンで選ぶ**(手入力ではない)。借方・貸方それぞれに2つの枠があり、
左が税区分(課税仕入10%/軽減8%/8%(旧税率)/非課税仕入、課税売上10%/軽減8%/8%(旧税率)/
非課税売上、対象外(不課税))、右がインボイス区分(適格/区分80%/区分50%/控不)である。
インボイス区分は課税仕入にのみ付くものなので、**課税仕入を選んだときだけ有効**になり、
それ以外を選ぶと自動的に外れて選択できなくなる。借方・貸方で選択肢は共通にしている
(売上返品や値引では借方に売上科目が来るため、側では判断できない)。

**簡易課税の顧問先**では、売上側の税区分名に事業区分が入る(実データで
`課税売上込六10%`を確認)。入力JSONの先頭に`"sales_business_type": "六"`のように
第一種〜第六種を指定すると、チェック資料の選択肢がその事業区分の名称で作られる。
事業区分は顧問先ごとに固定なので、案件フォルダの`CLAUDE.md`に記録しておき、
JSONを作るたびにこの項目を入れること(本則課税の顧問先では指定しない)。

このHTMLは案件フォルダの中に出力されるため、開くのにフォルダを辿らずに済むよう、
**デスクトップに「仕訳チェック資料」というアイコンも自動で作成される**(既定の動作)。
利用者にはこのアイコンをダブルクリックして開いてもらうのが一番簡単である。アイコンは
常に最後に作成したチェック資料を指し、次に別の案件のチェック資料を作ると同じアイコンが
そちらに切り替わる(デスクトップにアイコンが増え続けないようにするため。過去の分は
案件フォルダのHTMLから開ける)。アイコンが不要な場合は`--no-desktop-shortcut`を付ける。

ユーザーにこのファイルを開いて確認してもらい、訂正があればその場で直してもらったうえで、
画面上の「変更をJSONとして保存(ダウンロード)」ボタンを押してもらう。これにより、
訂正後の内容が入力JSONと同じ形式のファイル(`<元のファイル名>_修正済み.json`)として
ダウンロードフォルダに保存される。

各伝票には**通し番号(No.1、No.2…)と、元になった証憑のページ**が表示される
(例: `証憑: 12月分 p.5` = 「12月分.pdf」の5ページ目)。利用者と「No.3の仕訳」の
ように指し示して会話でき、元の証憑のどこを見ればよいかもすぐ分かる。

**あとで確認したい仕訳には付箋を付けられる。** 各伝票の「🔖 要確認」を押すと
その伝票が黄色く強調され、見出しに「🔖 要確認 N件」と件数が出る。判断に迷った
仕訳や、利用者に確認したい仕訳を見失わないための目印である。この印は保存する
JSONに`needs_review: true`として残るので、**ユーザーから受け取ったJSONにこの印が
付いていたら、その伝票について何を確認したいのかを必ず尋ねること。** 印を付けた
まま先に進めてはならない。チェック資料を作り直しても印は引き継がれる。

**不要な仕訳は伝票ごと削除できる。** 各伝票の右上にある「🗑 伝票ごと削除」を押すと、
その伝票が「削除予定」になり、保存するJSONから除かれる(証憑の重複・対象外の書類が
混ざっていた場合などに使う)。**押した時点では消えず、内容を確認できる状態のまま
薄い表示になるだけ**で、「元に戻す」でいつでも取り消せる。実際に除かれるのは保存
ボタンを押したときで、そのとき何件除かれるかが表示される。すべての伝票を削除予定に
した場合は保存できない(空のファイルを作らないため)。

**画面で行った訂正は、そのブラウザに自動で一時保存される。** このHTMLは生成時のデータを
埋め込んだ固定ファイルで、「変更をJSONとして保存」は別ファイルをダウンロードするだけ
なので、そのままでは同じHTMLを開き直すと訂正前の状態に戻ってしまう。それを防ぐため、
訂正するたびにブラウザ内へ保存し、**開き直したときは前回の訂正内容が復元される**
(画面上部に「前回この画面で行った訂正内容を復元しました(○月○日 ○○:○○時点)」と
表示され、不要なら「破棄して最初の状態に戻す」で消せる)。作業を中断して閉じても、
続きからやり直せる。なお保存先はそのPCのそのブラウザ内なので、別のPCや別のブラウザで
開いた場合は復元されない。

ユーザーから「訂正して保存した」と連絡を受けたら、そのダウンロードされたJSONファイルの
場所を確認し、**そのファイルを次の手順の入力として使う**(手順4のJSONを自分で編集し
直す必要はない)。なお、この画面での訂正は「借方金額と貸方金額を常に同じ値として同期
させる」「1伝票内の明細行の追加・削除」までは対応しているが、複合仕訳で分割している側
の判定(`split_side`)を明示的に変更する操作までは対応していないため、そこまでの修正が
必要な場合は手順4のJSONを直接編集する。

### 6. 弥生形式に変換する

チェック資料での確認・訂正が終わったら、その時点の最新のJSON(訂正があれば手順5で
ダウンロードされた`_修正済み.json`、無ければ手順4のJSON)を使って最終ファイルを作成する。

```
scripts\.venv\Scripts\python.exe scripts\generate_yayoi.py "<最新のJSON>"
```

貸借不一致など問題があればエラーメッセージが表示され、ファイルは出力されない。その場合は
JSONの該当箇所を修正して再実行する。成功すれば、そのまま弥生会計にインポートできる
CP932テキストファイルが出力される。

**出力先(既定はデスクトップ)**: 上記のように出力先を省略すると、デスクトップに
`仕訳インポート_YYYYMMDD.txt`として出力される。案件フォルダの奥に生成すると利用者が
見つけにくいためであり、**通常はこの既定のまま(出力先を指定せずに)実行する。**

**デスクトップに出したい場合は、必ず出力先を省略すること。自分でデスクトップの
パスを組み立てて渡してはならない。** 案件フォルダの`CLAUDE.md`の「インポート用
ファイルの生成先」が「デスクトップ」(既定値)のままの場合も、指定とはみなさず
省略する。OneDriveのバックアップが有効なPCでは実際のデスクトップが
`OneDrive\デスクトップ`に移っており、`C:\Users\<名前>\Desktop`は使われていない
古いフォルダとして残っていることがある。そこへ出力すると、エラーにならないまま
利用者からは見えない場所にファイルが置かれる(PCごとに出力先が違って見える
原因になる)。省略した場合はスクリプトがWindowsに正しい場所を問い合わせるので、
どのPCでも利用者から見えるデスクトップに出る。

**`CLAUDE.md`にフルパス(例: `Z:\共有\会計データ\2026年度`)が書かれている場合だけ**、
その場所を優先して明示的に渡す(顧問先ごとの共有フォルダに置きたい場合など):

```
scripts\.venv\Scripts\python.exe scripts\generate_yayoi.py "<最新のJSON>" "<CLAUDE.mdで指定された生成先>"
```

出力先はフォルダでもファイル名でも渡せる(フォルダを渡した場合は、その中に既定の
ファイル名で出力される)。同じ日に複数回実行した場合、既にあるファイルを上書きせず
`仕訳インポート_YYYYMMDD(2).txt`のように番号が付く。実行結果に実際の出力先パスが
表示されるので、**利用者にはそのパスをそのまま伝えること**(番号が付いた場合に、
どのファイルを取り込むべきか迷わせないため)。

### 6b. 弥生会計の代わりに会計大将のCSV形式で出力する場合

顧問先が弥生会計ではなく**会計大将**を使っている場合、手順6の代わりに以下を使う。
会計大将のCSV取込仕様は公開されていないため、この機能は実際の顧問先(会計大将
利用)からエクスポートされた実データを解析して実装したものであり、**弥生会計向け
機能に比べて対応範囲が限定的**であることを踏まえて使うこと。

**現時点の制限**:
- 1伝票1明細の単純仕訳のみ対応(`split_side`を使う複合仕訳は非対応。複合仕訳が
  必要な場合は素直に弥生形式(手順6)を使う)。
- 補助科目は非対応。会計大将は補助科目も数値コードで管理しており、その対応表を
  受け取る仕組みがまだ無いため、`sub_account`が入っているとエラーになる
  (黙って捨てて誤ったデータを出すことは避けている)。区別が必要な情報は摘要欄に書く。

**税区分**: 名称は手順3で説明した一覧(弥生・会計大将共通)をそのまま使う。会計大将
出力に特有の制約は以下のとおり:

- **旧税率8%(軽減ではないもの)は未対応**(実行するとエラーになる)。会計大将側の
  実データが無いため、意図的に未対応にしている。必要になった場合は、その税率を
  使った既存の会計大将エクスポートCSVを入手して規則を確認するところから始めること。
- **免税事業者等からの課税仕入(インボイス制度の経過措置)**は、税区分名に控除割合
  まで含めれば(`課対仕入込10%区分80%`など)、消費税額は自動で計算される(実データの
  経過措置190行と税額まで一致することを確認済み)。`tax_amount`に0以外を明示した
  場合は、その値が優先される。
- 消費税額の計算式: 標準10%は金額×10/110、軽減8%は金額×8/108。経過措置は
  その割合(区分80%→80%、区分50%→50%、控不→0%)を掛けた額になる。

**追加で必要な入力**: 会計大将は勘定科目を名称ではなく数値コードで管理しており、
そのコード体系は顧問先ごとに異なる。そのため、案件の「参考資料ファイル」に
以下の形式のJSON(例: `会計大将科目コード表.json`)を用意してもらう必要がある
(無ければ、勘定科目一覧表などの資料と合わせてユーザーに確認しながら作成する)。

```json
{
  "fiscal_start_month": 2,
  "accounts": {
    "旅費交通費":   {"code": "636", "cash_flow_type": "2", "cash_flow_code": "18"},
    "法定福利費":   {"code": "627", "cash_flow_type": "2", "cash_flow_code": "15"},
    "売上高":       {"code": "410", "cash_flow_type": "1", "cash_flow_code": "2"},
    "現金":         {"code": "111"}
  }
}
```

- `fiscal_start_month`: その会社の会計年度が何月始まりか(1-12)。安易に2月始まりだと
  仮定せず、勘定科目一覧表や総勘定元帳など、その会社の実際の資料から確認すること。
- `cash_flow_type` / `cash_flow_code`: 資金繰り(資金収支)表での分類。会計大将の
  エクスポートCSVでは「資金繰コード」「資金繰名」として出てくる項目にあたる。
  **現金・預金の側ではなく、その相手科目(費用・収益・債権債務などの「理由」側)に
  設定する**(実データで、同じ手数料を現金/A銀行/B銀行のどれで払っても常に同じ値に
  なることを確認済み)。`cash_flow_type`は`1`=入金・`2`=出金。`cash_flow_code`は
  資金繰り区分の番号(例: 18=販売管理費、15=人件費、3=売掛金入金、2=現金売上)で、
  科目コードから機械的に導出できないため、その会社の会計大将エクスポートCSVから
  該当科目が使われている行を探して確認する。設定しなかった科目は資金繰り対象外
  (共に`0`)として出力される。

準備ができたら以下を実行する。出力先の扱いは手順6とまったく同じで、**省略すると
デスクトップに**`仕訳インポート_YYYYMMDD.csv`として出力される。**デスクトップの
パスを自分で組み立てて渡してはならない**(理由は手順6を参照)。`CLAUDE.md`に
フルパスが書かれている場合だけ、それを第3引数で明示的に渡す:

```
scripts\.venv\Scripts\python.exe scripts\generate_kaikei_taisho.py "<最新のJSON>" "<科目コード表.json>"
```

対応していない仕訳(複合仕訳・未対応の税区分・科目コード表に無い科目)が含まれる
場合は、その旨を示すエラーメッセージが表示され、ファイルは出力されない。

## 案件固有の気づきをCLAUDE.mdに記録する

作業中に、その案件(取引先)に固有の、次回以降も使えそうな気づき(例:「この取引先は
いつも○○という科目を使う」「この書類の××という文字はいつも誤読されやすい」など)に
気づいた場合、または利用者から「記録して」「覚えておいて」と言われた場合は、その案件
フォルダ直下の`CLAUDE.md`の「## この案件で得た気づき」の下に、以下の書式で1行追記する:

```
- [YYYY-MM-DD] 内容
```

見出しがまだ無い場合は、末尾に見出しごと新設してよい。

CLAUDE.mdには手順1で確認する項目もあり、初期状態はいずれも「未確認」になっている。
**手順1で利用者に確認したら、必ずこの行を書き換えておくこと**(次回以降、聞き直さずに
済むようにするため):

- 「## この案件の会計ソフト」 → 「弥生会計」または「会計大将」
- 「## 消費税の課税方式」 → 「本則課税」または「簡易課税(第六種事業)」のように
  事業区分まで書く(簡易課税の場合、種別が無いと売上の税区分を作れない)

同様に、自社のインボイス登録番号が判明した場合も「## この案件で得た気づき」に記録して
おくと、手順2の`--own-invoice-no`にそのまま使える。

「## インポート用ファイルの生成先」という項目もある。既定は「デスクトップ」で、
利用者がここをフルパスに書き換えている場合は、手順6・6bでその場所を出力先として
明示的に渡すこと(既定のままなら出力先を指定せずに実行する)。

**これらの記録はその案件フォルダに
だけ残るローカルな記録であり、他の案件やスキル本体(SKILL.md)には反映されない。**
特定の案件に限らず全社共通で使えそうな内容(摘要の書き方や複合仕訳の作り方など、
スキル自体の改善につながる気づき)は、CLAUDE.mdに書かず、利用者にその旨を伝えて
判断を仰ぐこと(スキル本体の更新・共有は利用者側で行う)。

## 借方・貸方どちらにも共通の実科目が無い複雑な仕訳(給与仕訳など)

手順4で説明した`split_side: "manual"`は、借方・貸方のどちらか一方に「全明細で
共通の実科目」がある場合の作り方だった。給与の総支給額から社会保険料・源泉税・
現金支給額などを差し引く仕訳のように、**借方・貸方のどちらにも共通の実科目が無く、
「複合」の出現側が明細ごとに入れ替わる**、より自由な複合仕訳も存在する(証憑書類
からの自動起票では通常発生せず、ユーザーから直接依頼された場合に対応する)。

この場合も`split_side: "manual"`をそのまま使えるが、「合計行→明細行」という構造が
成り立たないため、各行の`debit`・`credit`を(「複合」プレースホルダーが必要な側も
含めて)そのまま個別に指定する。どの行を先頭にするかは自由でよい。

```json
{
  "start_denpyo_no": 501,
  "legs": [
    {
      "voucher_id": "202607_payroll",
      "leg_no": 1,
      "transaction_date": "2026-07-25",
      "debit":  {"account": "役員報酬", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 500000, "tax_amount": 0},
      "credit": {"account": "複合", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 500000, "tax_amount": 0},
      "description": "役員報酬　7月分",
      "split_side": "manual"
    },
    {
      "voucher_id": "202607_payroll",
      "leg_no": 2,
      "transaction_date": "2026-07-25",
      "debit":  {"account": "複合", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 20000, "tax_amount": 0},
      "credit": {"account": "法定福利費", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 20000, "tax_amount": 0},
      "description": "社会保険料　6月分",
      "split_side": "manual"
    },
    {
      "voucher_id": "202607_payroll",
      "leg_no": 3,
      "transaction_date": "2026-07-25",
      "debit":  {"account": "複合", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 700000, "tax_amount": 0},
      "credit": {"account": "現金", "sub_account": "", "department": "", "tax_category": "対象外", "amount": 700000, "tax_amount": 0},
      "description": "給与及び通勤手当　7月分",
      "split_side": "manual"
    }
  ]
}
```

各明細の`debit.amount`と`credit.amount`は(その明細単独では)必ず一致させること
(バランスチェックの対象になる)。伝票全体としての借方合計・貸方合計は一致しなくてよい
(それがこのモードの目的である)。「複合」を書く側の税区分は`"対象外"`にする。

このモードで仕訳を作る場合も、証憑読み取りベースのフローと同様に、金額や科目の内容を
ユーザーに提示して確認を取ってから`generate_yayoi.py`を実行すること。可能であれば
手順5のチェック資料も作成して確認してもらうとより安全である(ただし現状のチェック
資料の画面編集機能は、`split_side`の値そのものを画面上で切り替える操作には対応して
いない)。
